# Marketplace repair release

Release worktree: `.tmp/ux`, branch `codex/marketplace-full-repair`. The original worktree and all `.env` files are preserved. This release remains closed to new live payments.

## Implemented

- Shared versioned purchase scope: included assets, exclusions, ongoing costs, timing and support. Seller publishing and explicit buyer approval precede checkout. The server controls the price; old payment-method selectors and missing checkout routes are removed.
- A committed reservation serializes buyers for one project. Provider retries reuse immutable parameters and a persisted generation. A provider lookup failure cannot silently mint another payment. Another buyer can proceed only once Stripe confirms the previous session expired. Unknown creation outcomes remain reserved for retry or reconciliation.
- Payment webhooks validate mode, session, reservation, amount, currency, charge and payment-intent identity. Database claims and business changes commit atomically. Failed writes roll back their claim, retain a failure code, and return HTTP 500 for Stripe redelivery. Distinct events for the same payment cannot create a second transaction.
- Platform commission and seller amount use the checkout snapshot in integer cents. Verified payment, held funds, delivered scope, current ownership, explicit receipt acknowledgment and a fresh unrefunded/undisputed provider charge are required for release. The transfer names its source charge and exact purchase group. A durable pre-call payout marker prevents an unknown payout from being retried after 23 hours, when the provider key might expire. Such cases require reconciliation.
- Legacy request-only ownership confirmation cannot complete a sale. Unpaid transfer progress is rejected. Checkout/handover locks listing edits, hold changes and deletion. Only the current owner can mutate uploaded files. Refund/dispute events block automatic release, including when they arrive before checkout confirmation; a dispute closing never automatically reopens a payout.
- Inquiries show the correct introduction, date and state; private conversation notifications link to the shared agreement. Sellers can upload handover files and mark delivery. Paid buyers can load/download files and open the exact receipt review. Missing assets can be reported before funds are released.
- Private file content is stored in PostgreSQL with authenticated access, safe download headers and legacy disk-read support. Limits: 10 MiB/file, 50 MiB/project, 200 MiB total for this deployment; uploads share a database lock for quota/memory control and a request limit. The budget is intentionally conservative for existing free infrastructure. Large repositories should be transferred through their hosting provider. Temporary files are removed after persistence; database deletions remove content atomically.
- Non-owner signed-in project reads use a public-field allowlist. Public visibility changes invalidate access immediately. New public tables retain RLS and no client-role grants. PostgreSQL certificate verification uses the existing Supabase CA.
- Successful login records activity. Known QA accounts can be explicitly tagged. Public sales/volume and profile completion metrics use verified released transactions, and business registration counts exclude tagged QA. Unclassified registrations are not proof of real or active users.
- Public HTML contains listing text and canonical metadata before JavaScript. Sitemap/robots return their real formats; private/missing listings and unknown pages return 404; account/filter routes are noindex; outages return 503 with retry guidance. A real share image exists. The guide/pricing/contact copy describes supported behavior and payment availability. The unrelated ebook is excluded from release assets and preserved locally.

## Operations and remaining launch conditions

1. **Email remains unavailable by user choice.** Existing Gmail SMTP is compatible with the server’s SMTP/EMAIL setting aliases, but Render Free blocks its ports. The user declined the $7/month upgrade and requested email setup remain pending. No credentials were moved and no new email provider was created. Password recovery and email notifications must not be represented as working. A verified HTTPS delivery integration or allowed SMTP hosting remains necessary for recovery; no actual reset email was tested.
2. **Keep `LIVE_COMMERCE_ENABLED=false` during release and operator setup.** The full isolated browser journey using Stripe-hosted sandbox Checkout has passed through seller transfer and buyer ownership. Its genuine provider event was retrieved through Stripe API polling and forwarded through a locally signed raw webhook. This establishes the isolated purchase lifecycle, not live production event delivery. Do not use test keys against the production app/database or artificial transactions with real cards. Observe the first legitimate sale only after the platform’s commercial setup is approved.
3. The live platform destination was verified on November 10 with checkout/refund/dispute coverage among 25 events. A separate connected-account destination for account updates remains optional setup. Preserve the existing platform webhook’s scope/signing secret. Checkout and Connect status also retrieve current seller capabilities, so stale local flags cannot by themselves enable payment.
4. Assign an accountable operator, verified support contact, handover deadline and refund/dispute policy. An admin can inspect payment failures at `/api/webhooks/events` and replay an original provider event at `/api/webhooks/replay/:eventId`. Normal users have no operational replay access. Review disputes/refunds and stale checkout/payout reservations manually; never clear an unknown payment reservation just because a local clock elapsed. A transferred chargeback may require reversal or another provider action; this release never moves money automatically for a dispute resolution.
5. Free Render can sleep and cold-start. Database-backed files survive its disk resets, but this plan is unsuitable for a promised uninterrupted payment/support SLA. The 200 MiB aggregate upload cap must be reviewed with actual database capacity before expansion.
6. Sellers still need real evidence: verify ownership, repository access, transferable rights, running costs, revenue and traffic for the two current sale listings. Their existence does not establish product quality or genuine activity. The three likely test registrations remain unclassified. Search Console, search impressions, qualified inquiries and conversion results remain unverified; technical SEO fixes do not establish visibility gains.
7. Have the terms/privacy/refund language reviewed for the operator’s actual business and jurisdiction before a broad paid relaunch. Current UI copy removes false claims; it is not a legal certification.
